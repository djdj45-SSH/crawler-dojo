# 上云版：同一套防护在真实边缘环境里

本地靶场（`server/`）教**机制**，这一节教**代价**。
两者合起来才是完整的：不理解代价，就会写出"看起来很安全"的配置，
然后在某天发现留言板挂了。

---

## 两种实现，差在配额

Cloudflare 免费版上，"按身份返回不同内容"有且只有两条路：

| | 方案 A：边缘重定向规则 | 方案 B：Pages Functions 中间件 |
|---|---|---|
| 在哪 | 控制台 `Rules → Redirect Rules` | 仓库里 `functions/_middleware.js` |
| 能不能返回自定义页面 | ✅ 重定向到你自己的静态页 | ✅ 完全可控 |
| **消耗 Function 配额** | **否** | **是**（每个命中的请求 1 次） |
| 免费版条数 | **10 条**（够用） | 不限条数，但受 10 万/天限制 |
| 规则是否公开 | 否（在控制台） | 是（跟着公开仓库走） |
| 能读请求体 / 做有状态逻辑 | 否 | 是（签名、计数、渐进式） |

**结论：能靠重定向解决的，都别用中间件。** 中间件的位置是"重定向做不到的那些事" ——
蜜罐、渐进式响应、需要状态判断的逻辑。

### 方案 A 的真实实现

本项目的博客（`blog.djdj45.top`）用的就是方案 A，而且已经上线。
完整配置、验证命令、踩过的坑都在博客仓库的 **`tools/traps.rules.md`**，
可以直接拿去对照，不必在这里重复一遍。

一句话概括它的形状：

```
爬虫请求 --(边缘 Redirect 规则，按 UA 匹配，302)--> /traps/trap-python.html
        --(静态文件，200)--> 「认出你了：python-requests」
```

**整条链路零 Function 调用**，所以不消耗配额、不碰留言板、请求量无上限。

### 方案 B 的代价，具体到数字

`functions/_middleware.js` 放在 `functions/` 根目录时，它是一个**全局**中间件 ——
会命中**每一个**路由，**包括每一个静态资源**。一篇文章页 ≈ 1 次 HTML + 4 次静态资源
= **5 次 Function 调用**。免费额度 10 万/天 ÷ 5 ≈ 2 万次页面访问。

更麻烦的是配额是**共享的**：Pages Functions 和 Workers 用同一个池。
如果站点上还有别的 Function（比如一个基于 D1 的留言板 `/api`），
那么爬虫洪流烧光配额之后，**先挂的是留言板**：

1. 配额耗尽
2. Pages 的默认模式是 **fail open** —— Function 被绕过
3. `/api/*` 不再有 Function 处理，退化成静态资源查找
4. 留言板接口返回 404

所以 `_routes.json` 不是可选项。见下一节。

---

## `_routes.json` 是强制项，不是优化

加了 `functions/_middleware.js` 之后，必须同时提供 `_routes.json`，
否则每个静态资源请求都要跑一次函数。

本目录的 `_routes.json` 做了三件事：

- `include` 只列出**真正需要判断的 HTML 文档**（`/`、`/posts/*`）
- `include` 里的 **`/api/*` 是必须的** —— 这个文件决定"哪些路径调用 Pages Functions"，
  漏掉它会让留言板自己的 Function 不执行，直接 404
- `exclude` 掉 `/assets/*` 等静态资源

效果：一次页面访问从 5 次函数调用降到 **1 次**。

> ⚠️ Cloudflare 在「有 `functions/` 但没有 `_routes.json`」时会**自动生成**一份。
> 你手写一份就覆盖它了，所以必须把自动生成的内容一并考虑进去 ——
> 这是这类"优化"最容易翻车的地方。

---

## 三条硬约束

1. **绝不设 fail closed。** 默认的 fail open 在配额耗尽时会让静态资源照常服务；
   改成 fail closed，配额一满全站返回 1027 错误页。
2. **搜索引擎的 Verified Bot 必须白名单放行。** 否则 SEO 会静默受损，
   而且是最慢才被发现的那种受损。
3. **返回不同内容时用 4xx/5xx，不要用 200 伪装**（除非规则足够窄）。
   规则只匹配 `python-requests` 这类库 UA 时不存在对搜索引擎的差异化返回，
   用 200 是安全的；规则一旦放宽，性质就变了。

---

## 为什么不在这里把 L2–L5 也实现了

上云版**只保留 L1**，这是刻意的：

- L2 需要跨请求的计数窗口 → 要绑 KV 或 Durable Objects
- L5 需要校验签名时间窗 → 同样需要状态
- 而 Workers 免费版没有现成的 KV 绑定，接进来会把"看清代价"这个目标冲掉

**"先看清代价，再决定要不要往上加"本身就是这一节的教学目标。**
需要完整六级时，回本地跑 `python -m server.main` —— 那里没有计量规则来分你的心。
